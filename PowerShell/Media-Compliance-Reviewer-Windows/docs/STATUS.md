## Measurement boundaries

`tests/benchmark.ps1` generates 10,000 immediate user folders and 12,000 small PNG files with distinct complete-file fingerprints. It exercises 4 file workers and a 200-card WPF view. It records elapsed time, committed progress, process private/working-set peaks, queue retention, and UI-poll timings. Its default measurement window is 180 seconds; reaching that window requests resumable scan cancellation, not process termination.

The fixture contains no private media. It does not establish performance for hundreds of thousands of large images/videos, remote-share failure behavior, or multi-day scans. UI-poll timing is not a measurement of human input latency or full rendered-frame rate. Retain those distinctions when interpreting its JSON output.

My initial version 0.1.0 measurement on the development machine committed 12,000 file records in the 180-second window; the first user's remaining previews were still pending, so no user was reported complete. Resumable cancellation completed at 180.12 seconds. Peak process private memory was 187.74 MiB, peak working set 205.96 MiB, and peak reported queue retention 0.56 MiB. UI-poll time was 25.08 ms at the 95th percentile and 259.43 ms maximum. These measurements describe that earlier generated PNG fixture only; they do not describe the broader decoder package in version 0.2.0.

`tests/benchmark-mixed.ps1` measures the portable script, including startup, its decoder descendants and a 200-card WPF view. My version 0.2.0 generated 360-file mixed-format run completed all three user folders without scan errors in 22.27 seconds. Sampled combined peak private memory was 486.13 MiB and combined working set was 508.62 MiB. The main PowerShell process peaked at 484.38 MiB private memory. UI-poll time was 15.01 ms at the 95th percentile and 208.98 ms maximum. The single script was 101,030,042 bytes. Samples were taken every 50 ms, so shorter peaks may be missed.

My version 0.3.0 run of the same generated 360-file fixture completed all three users without scan errors in 26.50 seconds. Sampled combined peak private memory was 491.29 MiB and combined working set was 510.77 MiB; the main process peaked at 489.53 MiB private memory. UI-poll time was 67.50 ms at the 95th percentile and 502.41 ms maximum. The script was 101,098,251 bytes. This run was slower and had longer UI polls than the previous measurement; it does not establish a responsiveness improvement. All previews now use the bounded isolated helper.

This fixture uses small images, RAW-like containers with embedded JPEGs, generated HEVC HEIF and short videos. It exercises format variety and helper recycling, not large-file decoding pressure or collection-scale growth. The larger embedded decoder package has a substantial startup footprint; do not use the earlier PNG-only measurement as a memory estimate for this build.

Ordinary native scanning has no 2.5 GB/5 GB database cap. Large final-build import fields stream rather than using the page reader's 2 MiB text/8 MiB BLOB limits. Actual SQLite per-value limits still apply. Original retention has a separate projected-database guardrail of 2.5 GB or 5 GB and checks free working space. These scan measurements do not establish the memory use of large version 0.3.0 imports.

My version 0.14.0 generated package check retained, packaged, authenticated and exported a 2,147,483,649-byte original after removing its source. The exported copy matched the independently calculated full SHA-256. The measured pipeline took 76.69 seconds and sampled source-process private memory peaked at 123.80 MiB. A separate cancelled package operation stopped after actual ciphertext writes and removed its owned incomplete output. This local source-process measurement excludes portable startup, WPF input latency, network behavior and multi-day scans; it does not replace the portable-script memory measurements above.
